# TDD 详细规则与最佳实践

## 垂直切片原则

每个 TDD 循环应该覆盖**一个完整的垂直切片**——从前端到后端的一小段完整功能，而不是一层（如"先写所有 model 层"）。

### 好的切片
- ✅ 用户注册的验证逻辑
- ✅ API 查询参数的解析
- ✅ 某个计算函数的业务规则

### 坏的切片
- ❌ "先写所有数据库模型"
- ❌ "先写所有路由"
- ❌ "先写所有工具函数"

## 测试质量要求

### 必须覆盖
- 正常路径（Happy Path）
- 边界条件（空值、极限值、特殊字符）
- 错误路径（异常、非法输入）

### 测试结构（AAA 模式）
```
// Arrange — 准备测试数据和环境
// Act — 执行被测代码
// Assert — 验证结果符合预期
```

## 重构清单

重构时不改变行为，只改善：

- [ ] 消除重复代码（DRY）
- [ ] 提取有意义的函数/类
- [ ] 改善命名（变量、函数、类）
- [ ] 简化条件逻辑
- [ ] 减少嵌套
- [ ] 统一错误处理模式
- [ ] 添加必要注释（解释 why，非 what）

## 常见 TDD 错误

| 错误 | 后果 | 修正 |
|------|------|------|
| 测试太脆弱（耦合实现细节） | 重构时测试大量失败 | 测试行为而非实现 |
| 跳过 Red 阶段 | 无法确认测试有效性 | 先看测试失败 |
| Green 阶段写太多代码 | 测试覆盖不全 | 刚好让测试通过即可 |
| 跳过 Refactor | 技术债累积 | 每次循环都重构 |
| 测试覆盖 Happy Path 只 | 边界 Bug 漏网 | 写边界测试 |

## 适配说明

本 skill 适配当前环境的测试工具：
- Python: pytest / unittest
- Node.js: vitest / jest / mocha
- Shell: bats / shunit2
