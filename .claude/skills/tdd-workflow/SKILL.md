# TDD Workflow — 测试驱动开发

当接到开发任务时，执行以下 Red-Green-Refactor 循环。**每个功能/修复只处理一个垂直切片，完成后才进入下一个。**

## 核心规则

### 原则
1. **生产代码只为了让失败的测试通过而写** — 不多写一行
2. **测试失败必须证明失败原因正确** — 确认是代码缺失而非测试本身错误
3. **一个垂直切片一个循环** — 不跳步，不提前优化
4. **重构阶段不改变行为** — 只改善结构，测试继续通过
5. **测试也是代码** — 与生产代码同等质量要求

### 禁止行为
- ❌ 先写实现再补测试（这是"测试后补"，不是 TDD）
- ❌ 一次性写大量代码再测试
- ❌ 跳过失败的观察直接写实现
- ❌ 重构时修改功能行为

## 三阶段循环

### 🔴 Red — 写一个失败的测试

```
1. 理解需求：这个垂直切片要做什么？
2. 思考接口：API/函数签名应该是什么样？
3. 写测试：只测这一个切片的行为
4. 运行测试：确认失败 ✓（失败原因 = "功能未实现"）
5. 验证失败原因：确实是功能缺失，不是测试写错
```

**输出**：一个失败的测试 + 明确的失败原因

### 🟢 Green — 写最小代码通过测试

```
1. 写刚好够让测试通过的代码
2. 不优化，不美化，不提前抽象
3. 可以硬编码、写死、用最简单的方式
4. 运行测试：通过 ✓
5. 确认没有其他测试被破坏
```

**输出**：通过所有测试的实现

### ♻️ Refactor — 清理代码

```
1. 测试通过的前提下重构
2. 消除重复、提取抽象、改善命名
3. 优化设计但不改变行为
4. 运行全部测试：仍然全部通过 ✓
5. 审查代码质量：可读性、一致性、简单性
```

**输出**：干净且测试覆盖的实现

## 工作流模板

当用户提出开发需求时：

```
📋 任务分析
────────────────────
需求: [用户需求]
垂直切片拆解:
  1. [第一个小步]
  2. [第二个小步]
  ...

🔄 开始 TDD 循环
────────────────────

🔴 RED - Cycle [N]: [切片名]
  测试: [测试内容]
  预期失败: [失败原因]
  运行测试 → [PASS/FAIL]

🟢 GREEN - Cycle [N]
  实现: [最小实现]
  运行测试 → [PASS/FAIL]

♻️ REFACTOR - Cycle [N]
  改动: [重构内容]
  运行测试 → [PASS/FAIL]
  ✅ 测试全部通过
```

## 验收标准

循环完成后确认：
- [ ] 所有测试通过
- [ ] 没有未测试的生产代码
- [ ] 测试覆盖了正常路径和边界情况
- [ ] 代码已重构为干净状态
- [ ] 提交/记录变更
