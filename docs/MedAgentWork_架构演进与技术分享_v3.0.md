## 开场：一个真实的问题

**场景**：临床医学大三学生，期末考覆盖 5 个科目、12 个模块、数百个考点。手头有教材、笔记、考纲，但——

- 把知识点变成可练习的题目，需要命题经验
- 市面上题库要么太旧，要么与教材脱节
- 自己出题？100 道题至少需要 10 小时，质量还不可控

**核心假设**：能否让 AI 完成「教材 → 题库」的转化，同时保证医学上不能出错？

这就是 MedAgentWork 的起点。**13 个批次、2,923 道题、5 个学科**之后，这里是与「AI 不可靠」斗争的完整工程记录。

## 二、架构：为什么是 5 个 Agent，不是 1 个？

### 2.1 血泪教训——集成模式的失败

最初的 batch003 采用「集成模式」：**一个 Agent 同时出题、自检、自修**。结果：

| 问题 | 具体表现 |
|------|---------|
| 🔴 自我审查盲区 | 出题 Agent 对自己的产出缺乏批判距离，质检形同虚设 |
| 🔴 无独立质检 | 「质检」本质上只是格式化输出，漏检事实错误 |
| 🔴 无追溯日志 | 修改后无法追溯「改了什么、为什么改、是否回滚过」 |

**后果**：batch003（301 题）被用户要求**全部重做**，催生了 batch004（388 题）。

### 2.2 分离原则（不可妥协）

从 batch004 起确立的铁律：

```
❌ 集成模式                          ✅ 分离模式
一个 Agent 包办一切                  各司其职，互不越界

Agent 2 → 只出题，不自检             
Agent 3 → 只质检，不出题不改题        
Agent 4 → 只执行结构化修改，不自创    
Agent 1 → 只编排，不自产不自审不自修  
Agent 5 → 只综合复习资料              
```

### 2.3 文件系统即管线（核心设计决策）

**不引入 LangGraph / Airflow / 任何编排框架**。原因：

| 设计选择 | 说明 |
|---------|------|
| **交接方式** | 文件系统（JSON / Markdown），非 API 调用 |
| **模型异构** | Agent 2 用 qwen3.7-max 批量生产，Agent 3 用 Claude 精细质检——不同模型各司其职 |
| **人工可介入** | 每阶段产物是标准文件，可在任一节点暂停、审查、打回 |
| **零框架依赖** | 降低运维复杂度，不需要额外服务 |

```
MedAgentWork/
├── 输入素材/        ← 教材/笔记/考纲（用户放入）
├── 中间产物/        ← Agent 2 产出
├── 质检报告/        ← Agent 3 产出
├── 最终产物/        ← Agent 4 产出
├── 复习资料/        ← Agent 5 产出
├── GoldenSet/       ← 用户签收的金标准（Agent 不可写！）
├── workflow_state.json  ← 管线状态机
├── validate_options.py  ← 机械化选项校验（1,622 行）
├── gate_check.py        ← 4 门禁 + halt 信号（997 行）
├── healthcheck.py       ← 7 维度系统巡检（589 行）
├── save.py / ingest.py  ← 管线顺序锁 + 防覆盖 + 格式校验
└── maintenance.py       ← 6 任务自动维护
```

## 三、防御体系：从「相信 AI」到「不相信 AI」

### 3.1 核心认知转变

整个系统的演进史，本质上是一个认知转变：

```
batch003:  「AI 能做好，我们相信它」                  → 失败，全部重做
batch004-005: 「AI 做主力，人做最后检查」               → 部分通过
batch006-014: 「AI 会犯错，代码做第一道防线」           → 发现 25 起事件
batch015+:   「不做检查就无法推进——门禁强制」           → 当前状态
```

### 3.2 6 层纵深防御（Defense in Depth）

```
层1: SOUL.md 共享约束       ████░░░░  32条声明式规则
层2: validate_options.py    ██████░░  13条机械化检测（R1-R13）
层3: save.py + ingest.py    █████░░░  管线顺序锁 + 防覆盖
层4: gate_check.py          ██████░░  4门禁 + halt信号传播
层5: healthcheck.py         ████████  7维度127项巡检
层6: maintenance.py         ████████  6任务自动维护
```

**关键设计**：每一层从上一层接过「漏网之鱼」。LLM 幻觉可能绕过层1，但会在层2被机械化规则捕获；如果层2有盲区，层4的门禁会在状态转换时阻断。

### 3.3 Orchestrator-as-Enforcer（HC-12）

来自 5 起管线绕过事件的教训。从 batch015 开始，**Agent 1 不再「善意提醒」，而是「强制门禁执行器」**：

```
每次状态转换：
  1. 运行 validate_options.py（Agent 2 产物）
  2. 运行 gate_check.py（门禁判定）
  3. 验证未通过 → halt=true → 不可推进
  4. Agent 1 不可在此检查上"相信下游自觉"
```

### 3.4 选项设计：从字数约束到结构模板（HC-14）

这是项目中最具启发性的 LLM 工程教训。

**问题**：我们用「选项 8-15 字」约束 Agent 2，结果：
- batch007 v1：LLM 理解不足，选项短至 3.9 字
- batch007 v2：加「≥8字+不足附加释义」→ 过度执行，膨胀至 18.9 字
- batch009→010：反复调整参数，始终在 3.9 ↔ 18.9 字之间摇摆

**根因**：**Prompt 阻抗不匹配（Defect B）** — 自然语言的参数约束被 LLM 过度或不足执行。

**解决方案**：用「结构模板」替代「字数范围」：

```
❌ 旧：「每个选项 4-12 字，长度比 ≤1.5x」
   → LLM 不理解"字数"，反复矫枉过正

✅ 新：「5个选项共享同一语法结构，如都是[部位]+[疾病名]」
   → LLM 理解"结构模板"，自然产出长度一致的选项
```

**核心原则（永不违背）**：
- ❌ 绝不告诉 LLM「选项 8-15 字」
- ❌ 绝不对选项做 `text[:n]` 截断（必然语义残片）
- ✅ 告诉 LLM「5 个选项共享同一语法结构」
- ✅ 用 LLM 语义压缩替代机械截断

## 四、机械化校验层：validate_options.py 规则矩阵

这是系统中最稳定的质量防线。**1,622 行 Python，13 条规则**，在 LLM 质检前过滤低级错误：

| 规则 | 检测内容 | 严重度 | 驱动事件 |
|------|---------|:--:|------|
| R1 | JSON 结构合法性 | FAIL | — |
| R2 | 选项长度比（max/min） | FAIL(>2.0) / WARN(>1.5) | batch007 振荡 |
| R3 | 数值升序排列 | WARN | — |
| R4 | 否定词加粗 | WARN | — |
| R5 | 选项数量检查 | FAIL | — |
| R6 | 数值干扰项区分度（>5x） | WARN | 题245 事件 |
| R7 | 截断检测（句号短选项/双点/1-2字残片） | FAIL | batch006 272题截断 |
| R8 | 最小长度+连接词结尾 | FAIL | batch007 96题截断 |
| R10 | 词重复线索（NBME D18） | FAIL | batch011 |
| R11 | 收敛策略（NBME D19） | WARN | batch011 |
| R12 | 无意义后缀检测 | FAIL | batch006/011 |
| R13 | 长度上限（>20字FAIL，avg>18字WARN） | FAIL/WARN | batch007/009 |
| — | （R9 缺单位检测，P1 待实现） | — | batch014 |

**设计原则**：代码能做的不让 LLM 做。LLM 擅长语义判断（「这个选项合理吗？」），但不擅长精确计数和模式匹配（「这个选项是否被截断了？」）。

## 五、从教训中生长：4 类系统性缺陷 × 25 起事件

经过 batch001→014 共 **25 起已记录事件**的根因分析，所有问题可归入 4 个系统性缺陷：

### 缺陷 A：声明式规则（5 起管线绕过）

| 批次 | 绕过事件 | 驱动规则 |
|------|---------|---------|
| batch006 | Agent 2 未跑 validate 即交付 | 产出门禁规则 |
| batch005 | B1 型 D20=0 但 PASS_WITH_FIXES | D20 门禁规则 |
| batch014 | 补丁只打到 COMPLETE 未溯源 | HC-13（新增） |
| batch009 | 调用指令覆盖短术语豁免 | — |
| batch011 v1 | Bloom 54.1% 未阻断 | Bloom 门禁（新增） |

**本质**：SOUL.md 写了「应该做 X」，但没有架构级强制执行（「不做 X 就无法继续」）。

**修复**：HC-12 Orchestrator-as-Enforcer + gate_check.py 硬阻断。

### 缺陷 B：Prompt 阻抗不匹配（4 起振荡）

自然语言约束被 LLM 过度/不足执行。典型案例：选项 18.9字 → 3.9字 → 18.9字，3 个 batch 反复摇摆。

**修复**：HC-14 结构模板替代字数范围。

### 缺陷 C：状态-文件系统漂移（6 起不一致）

workflow_state.json 记录的状态与实际文件系统不同步。

**修复**：healthcheck.py [B] 文件完整性检查 + [C] 状态一致性检查自动化。

### 缺陷 D：零自动化运维（10 起「记得就做」）

根污染、Prompt 同步、跨区同步、归档、回归测试——全部依赖人工记得触发。

**修复**：maintenance.py 6 任务定时维护 + 三层自动化运维体系。

## 六、三大截断灾难——选项质量的「至暗时刻」

### batch006：272 题截断

第一次大规模 QA 失败。Agent 2 产出中包含大量 `text[:n]` 暴力截断——「LVEF大于等于」丢了「40%」，「急性前壁心肌」丢了「梗死」。

**教训**：`text[:n]` 截断 = 语义残片。任何对医学文本的字符级截断都是灾难。

### batch007：96 题含截断，74 题受影响

第二次更隐蔽。LLM 系统性产出以连接词结尾的选项（「的/和/与/于」），逗号顿号截断痕迹明显。

**教训**：LLM 的自然截断倾向需要机械化规则（R8）对冲，不能靠 Prompt 约束。

### batch014：19 处回归

第三次发生在以为已经修复之后。补丁只打到 COMPLETE.json，下次合并时源文件中的旧截断又回来了。

**教训**：HC-13 补丁溯源强制——修复 COMPLETE 必须同步修改分系统源文件。

## 八、三元协同：代码 × LLM × 人工

```
代码层（机械化）  → 格式校验、数值比对、截断检测、占位符检测
                  → 确定性规则，100% 准确，零幻觉

LLM 层（推理）    → 事实准确性、逻辑一致性、干扰项质量、Bloom 层级
                  → 语义理解、多步推理、开放判断

人工层（签收）    → 升级告警审查、金标准确认、考试适配判断
                  → 最终决策、伦理判断
```

**核心理念**：不是「AI 替代人」，而是「AI 做 AI 擅长的事，代码做代码擅长的事，人做人擅长的事」。
